# Общий входной роутер

Это самостоятельный Compose-проект `edge`. На сервере он находится в
`/opt/edge` и не зависит от Compose-проектов приложений. Каталог можно
перенести в отдельный инфраструктурный репозиторий без изменения приложений.

Роутер владеет публичным портом 443, HTTPS, сертификатами и таблицей
маршрутов. Приложения владеют своим runtime, данными и аутентификацией.
Только их HTTP-шлюзы подключаются к внешней Docker-сети `edge`; базы,
хранилища и Java-приложение YesIHave остаются в сети своего проекта.
Docker socket не монтируется, контейнеры не обнаруживаются автоматически.
Новый маршрут включается явно через файл конфигурации.

## Запуск

Скопируйте этот каталог в `/opt/edge`, `.env.example` в `.env` и задайте
`EDGE_PUBLIC_IP`. Создайте общую сеть один раз:

```sh
docker network inspect edge >/dev/null 2>&1 || docker network create edge
cd /opt/edge
docker compose config --quiet
docker compose run --rm --no-deps caddy caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
docker compose up -d
docker compose logs --tail=50 caddy
```

Для IP используется доверенный сертификат Let's Encrypt `shortlived` с
автопродлением, для доменов — обычный ACME-профиль. Проверка владения
выполняется на порту 443 (TLS-ALPN-01). Порт 80 не используется роутером:
на текущем сервере он остаётся у masterclass. Не закрывайте публичный 443,
иначе продление сертификатов не сможет пройти. HTTP не перенаправляется
на HTTPS; открывайте адрес с явным `https://`.

В томах `edge_caddy_data` и `edge_caddy_config` находятся ACME-аккаунт,
сертификаты, ключи и служебная конфигурация. Сохраняйте их при обновлении
и резервном копировании; `down -v` для обновления не нужен.

## Подключение другого проекта

В Compose этого проекта подключите только его web-сервис к сети `edge`.
Назначьте уникальный сетевой alias; не используйте общий `app` или `nginx`:

```yaml
services:
  web:
    # image, volumes, environment — настройки самого приложения
    networks:
      default:
      edge:
        aliases: [example-web]
networks:
  edge:
    name: edge
    external: true
```

Не публикуйте внутренний HTTP-порт через `ports`. Для диагностики при
необходимости привяжите его только к `127.0.0.1`. Внешняя сеть — доверенная
зона: подключённые шлюзы видят друг друга; это не изоляция для недоверенных
контейнеров. Сервисы, которым нужна защита входа, должны обеспечивать её
сами или отдельным middleware; наличие маршрута не добавляет пароль.

### Вариант 1: отдельное имя

Направьте DNS имени на сервер и добавьте
`/opt/edge/routes/hosts/example.caddy`:

```caddyfile
https://example.your-domain.test {
    reverse_proxy example-web:8080
}
```

Замените демонстрационное имя своим реальным доменом. Так приложение
работает от `/` и не требует поддержки префиксов.

### Вариант 2: путь на том же IP

Добавьте `/opt/edge/routes/ip/10-example.caddy`:

```caddyfile
handle_path /example/* {
    reverse_proxy example-web:8080
}
```

Адрес: `https://<IP>/example/`. `handle_path` удаляет `/example` перед
передачей запроса. Приложение должно поддерживать внешний base URL
`/example/` для ссылок, ресурсов, cookies и redirects. Прокси сам это не
исправляет. Используйте `handle`, если upstream ожидает префикс целиком.
Корневой маршрут YesIHave — fallback; специфичные пути обрабатываются раньше.
Приложения на путях одного IP имеют общий browser origin: это не отдельная
граница безопасности для cookies, хранилища браузера и Basic Auth.
Подключайте так только доверенные сервисы; для независимых приложений
предпочитайте разные доменные имена. Для upstream без аутентификации
можно явно удалять `Authorization` через `header_up -Authorization` внутри
`reverse_proxy`, чтобы не передавать ему Basic Auth другого приложения.

## Применение маршрутов

После подключения web-контейнера и добавления файла:

```sh
cd /opt/edge
docker compose exec -T caddy caddy reload --config /etc/caddy/Caddyfile --adapter caddyfile
curl -I https://<IP>/example/
```

`reload` проверяет новую конфигурацию перед переключением: при ошибке
прежняя продолжит работать. Перезапускать YesIHave и другие приложения
не нужно. Проверяйте доступ снаружи без `curl -k`, включая аутентификацию
и загрузку ресурсов конкретного приложения.

YesIHave подключается через свой `compose.vds.public.yml` с alias
`yesihave-web`. Его обычное обновление или остановка не управляет роутером.

Из корня исходного репозитория можно проверить границы стеков без Docker
daemon: `python3 scripts/check-deployment-config.py`. Проверка требует только
Docker Compose CLI и использует example-файлы, а не реальные пароли.
